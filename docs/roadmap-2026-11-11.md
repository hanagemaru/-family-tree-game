# 家系図ならべ：継続プレイ・スコア・出題データ・カード画像（2026-11-11）

## 状況と確定した考え方

- 2026-11-11に一体型ゲームテーブル／山札／徳川18枚・競走馬24枚を含むPR #1をmainへマージ済み。
- 親子・兄弟姉妹・夫婦（競走馬は父母と産駒）を知ること、**繰り返し遊んで家系・血統を覚えること自体を実力向上として評価**する。学習や記憶によるスコア上昇を抑制しない。
- 競走馬テーマは継続開発の**重点候補**。収益需要が高いと断定はせず、テストと実ユーザー反応で検証する。
- 画像や写真は未対応。カードの表面図柄はテーマ内で共通の抽象図柄（個別識別には名前が必要）。

## ゲームとして検討する設計（未実装・数値も未決定）

### 知らないカードへの対応

1. 既存の2段階ヒント（人物・馬の説明→具体的な関係）を残す。
2. 保留プール1枠：手札から1枚を横に保管し、山札から補充。保管カードは後に戻せる。手札6枚と同等になる面があるが、**保管対象を選ぶ判断**が生まれる。
3. 選択札1枚だけ山札の後ろへ送り直す。無制限・無料にせず、コストやスコア影響を検証。
4. 正解・クリア回数等に応じてプール枠や手札上限を解放する長期報酬も選択肢。付与条件・永久アンロック／ステージ内限定などは未決定。
5. これらを一度に実装せず、追加ルールなしで完走できることを維持し、複雑さと有用性を比較する。
6. 「置けるカードがない状態」を防ぐ現在の自動補充処理は保持。プレイヤーが単に関係を知らないことと、物理的に配置不可能なことは区別する。

### スコアと競争

- 完走を前提に、クリア時間・ヒント（段階別）・誤答・カード送り直し／プール利用等を記録し、スコアへ反映する。
- 時間だけの最速競争にはしない。学習を妨げるような過大な時間減点を避ける。具体式・重み・ベスト判定はプレイ時間と難易度実測後に決定。
- 親子関係を覚えた上での高速クリアは正当な実力。
- 難易度・カード枚数・問題生成条件が違うスコアは同じランキングへ無補正で混ぜない。
- **フリー**：毎回異なる家系図を生成し、自己ベストを狙う。
- **デイリー／週間**：同一問題ID・同一カードセットを全員に配布して競争。再挑戦スコアの扱い（初回限定／ベスト等）は未決定。チートや多重挑戦対策も未決定。
- ゲーム内通貨・ランキング・アカウント・サーバー保存は現時点で未実装。

### 大きなデータベースからのランダム生成

- 多数の人物・競走馬を「個体ID・表示名・親ID・性別・世代・特徴・データ出典・画像の権利情報・難易度」で保持し、1プレイごとに固定枚数（例：18／24枚）を抽出する。
- 先に起点を選び、そこから親子・兄弟などで接続する候補を拡張して、**選ばれた全員が最終的に場へ配置可能**な連結部分グラフを作る。
- 単にランダムな個体を取り出すだけでは成立しない。推定関係・同名馬・親子不明・養子/実親混同・競走馬の同名別個体などは検証／除外。
- 親子関係とステージ内の「兄弟」判定が妥当なこと、生成した問題の到達性、出題分布、山札補充で詰まないことを自動テスト。
- 難易度は (1) 個体の知名度、(2) 出題される関係の知名度、(3) 母系・傍系・世代数、(4) 実プレイの正答率を用いて段階的に補正。
- 知名度の代理指標（Wikidata情報量、Wikipedia記事、閲覧数など）は不完全。難易度確定前に実プレイの回答率で検証する。
- ランダム生成と固定ランキングの両方で問題IDと乱数シード・データ版を保存し、再現可能にする。

## 競走馬データベース検証（初回の実データ検証済み）

1. CC0で公開されるWikidataの構造化データから、**父 P22・母 P25**（Wikidata公式の馬のSPARQL例に準拠）を取得。
2. 日本の著名馬（現在の24頭を中心）のIDを確認し、父母関係の欠損率・内部で連結する頭数・取れる世代の深さを実測する。
3. 一部のみのデータでどれくらい18〜24頭の「毎回変わる」問題が作れるか試作し、抽出失敗理由を列挙する。
4. 不足分は許諾を得たデータソースまたは出典を確認した少数の手入力で補完。競馬サイトの商用再配布不可データを無断で収集・再配布しない。
5. 将来は別ジャンルの家系にも適用できる一般的な親子グラフ形式にする。

## 次の課題：カードに表示する個別の絵・写真

- 現状のカードは全員ほぼ同じシルエットで、視覚的な区別がしづらい。競走馬の魅力も伝わりづらい。
- **写真を使う案**：Wikimedia Commons等で個別ファイルのライセンス・作者・クレジット・改変条件・出典URLを確認して使う。Wikidataの `P18` は**画像参照であってライセンス許諾ではない**。JRA・新聞・競馬ポータルの写真は、公開されているだけでは転用不可。
- **イラスト案**：権利が明確な独自制作・委託・適切に許諾された素材。外見の違い、毛色、装備などを反映できるが、すべての馬の正確な肖像として扱わない。
- **ハイブリッド案（有力）**：権利確認済みの馬は写真、その他は独自のカード図柄／特徴的な装飾。個体の識別はカード名を最優先。写真の出典・ライセンスへのリンクをクレジット画面に保持。
- 画像の取得・撮影・公開は行っていない。写真カバー率は血統データと同様に実測する。
- 競走馬の肖像に騎手や勝負服が写り込む場合は、写真の利用許諾以外の問題（権利・利用範囲）も必要に応じて確認する。

### 2026-11-12：カード画像の採用・容量方針（採用方針、未実装）

**基本方針：画像の有無で出題対象を制限しない。** 有名馬・良質な権利確認済み写真がある馬は実写真を優先し、写真がない馬は情報に応じて軽量な代替ビジュアルを表示する。

1. **実写真**：著名馬を優先。ただし知名度だけで厳密に限定せず、マイナー馬でも利用条件を満たす良い写真があれば使う。Commons画像も各ファイルごとに著作者・ライセンス・出典・改変条件を確認する。
2. **特徴を反映した共通イラスト**：写真がないが毛色・性別などの情報がある馬。馬ごとに個別ファイルを大量生成するのではなく、数種類のSVGテンプレートをデータに応じて着色・調整する。事実にない顔の模様・体格などを正確な肖像として見せない。
3. **汎用デザイン**：特徴データが不十分な馬。共通シルエットや血統テーマの装飾を使い、馬名を識別の主体とする。イラストを無理に捏造しない。

**ストレージと配信**

- 写真はカード表示サイズに合わせて圧縮し、WebPなどの軽量形式と必要なら小さいサムネイルを用意する。
- 概算：平均40KB/枚と仮定した場合、100枚=約4MB、1,000枚=約40MB、5,000枚=約200MB。*実測値ではない*ため、複数写真で画質・サイズの確認が必要。
- 大量写真はGitHubのソースリポジトリに直接格納せず、画像配信用のストレージ/CDNを検討する。
- ゲーム開始時に全馬の画像を読み込まない。場・手札など実際に表示するカードだけ遅延ロード・キャッシュし、画像がなくてもゲームが進行するようにする。
- 共通イラストはSVG等を共有して、馬の頭数に比例したストレージ増加を避ける。

**次の試作と判断基準**

- 現行の24頭から権利確認済み写真を数枚選び、**写真カード／特徴別イラストカード／汎用カード**を同じテーブル上で比較する。
- 名前の可読性、画像の判別しやすさ、トリミング、読み込み速度、写真とイラストの統一感を実機で評価する。
- 写真ごとのライセンス表記を管理し、ゲーム内の詳細・クレジットで必要情報を見られる設計にする。
- 今回は方針の記録のみ。写真素材の配信・個別馬イラスト生成・UI実装・容量実測は未実施。

## 開発優先順位

1. Wikidataの**実データ**で著名馬周辺の父母グラフ・欠損率・連結性を検証。
2. 課題と出典をデータレポートとして保存し、適切なデータ供給方法を決定。
3. 個別カード画像のライセンスと入手可能率を試作評価。
4. プレイ中の「わからない時の選択肢」と点数制を小規模A/Bで検証。
5. ランダム生成→難易度→デイリー共通出題・ランキングの順に実装。
