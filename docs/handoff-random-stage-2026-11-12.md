# 次セッション引き継ぎ：18枚ランダム血統問題の生成（2026-11-12）

## 目的

競走馬のWikidata由来の父・母データから、1プレイ **18枚（起点1枚＋手札・山札17枚）** の、すべてつながった家系図／血統図を再現可能にランダム生成する。まずは**実データを用いた問題生成・評価の成立性検証**を完成させる。写真・ランキング・スコア・プール等は今回の対象外。

**状態：計画を記録した段階で、ランダム生成器は未実装。** 既存の固定ステージは徳川18人、競走馬24頭。旧ゲームを壊さない。

## これまでの確認結果と注意

- 40頭の有名馬をWikidataで識別。現行24頭の父情報は24/24、母情報は21/24。ディープ周辺の部分取得で285頭が連結。
- 別の調査では13起点に直接つながる子として**重複除外705頭**を取得。ただし285と705は**調査範囲・方法が違い、足し算しない**。
- 母系の欠損が目立つ。Wikidataの登録数は実産駒数ではない。**構造化データがある＝実際の親子関係を確証した、ではない**。
- 調査の生JSONはGitHub Actions成果物として出力されるが、**リポジトリに全件データが必ず格納されているわけではない**。後続処理に必要な小型スナップショットは、再実行・検査したうえでバージョン付きファイルとしてリポ内に保存する。
- Wikidataの構造化データはCC0。JRA・JBIS等の二次利用制限付きサイトを無断スクレイピング／転載しない。
- 写真・イラストは別件。現行24頭のCommons画像ライセンスの調査結果は既にあるが、画像自体の実装は未着手。

## 次の作業：2段階で着手

### フェーズA：血統データを実行可能な問題データに整備

1. mainのコード仕様（各馬のID、`parents`、`generation`、`stage.anchor`、`ensurePlayable`、配置／家族線）を確認。
2. Wikidataの公開APIと既存スクリプトから、**複数の系統をカバーする取得済み父P22・母P25のグラフ**を構築。公開APIの呼び出し回数とスナップショット容量を抑える。
3. QIDを一意なキーにしたゲーム用のJSONを生成。日本語名、父母QID、出典、欠損状態、任意の毛色・画像参照などを持たせる。生データと出題用データを分離する。
4. 同名異馬、重複関係、自己親、世代矛盾、循環、存在しない参照、父母の取り違えを可能な限り検査。信用できないエッジは除外し、除外理由をレポートに残す。
5. ゲームの`generation`は相対的な整列用世代として計算する。個体の生年をただ代用せず、親子の整合性を優先する。
6. 再現性確保：データ版・取得日・出典・加工方法を記録し、ローカル／CIで同じスナップショットを使って検証できるようにする。

### フェーズB：18枚の部分グラフ生成・大量検証

1. シードつき疑似乱数で起点を選び、親・子・兄弟がいる複数方向に拡張。**18頭すべて、ゲームで成立する関係を通じて配置可能**であることを必須条件にする。
2. 必須条件：重複なし、孤立なし、全員の配置順に少なくとも1つの完成ルートがある、ゲームが使う関係判定と矛盾しない。
3. 良問のソフト条件：おおむね3〜5世代、2〜3か所以上の分岐、父母系・子孫・兄弟の適度な混合、スター種牡馬1頭の産駒ばかりにならない、画面上の交差・横長・縮小が過剰でない。
4. 多数の候補から構造評価スコアの高いものを選ぶ。**例示の比率を固定制約にしない**。そもそも成立しない場合は条件緩和の実測結果を提示する。
5. **最低100パターン、可能なら1,000パターン**を異なるシードで生成・検証。成功率、失敗理由、重複率、出題馬の偏り、起点の系統、世代範囲、分岐数、線の交差、想定倍率を集計する。
6. `ensurePlayable`、`place`、`relations`、`diagram`などの既存ロジックを可能な限り利用し、実際のゲーム状態で**18枚完走できること**を自動テスト。祖先だけの連結性判定では不十分。
7. シード／出題ID／採用18頭／データ・生成器のバージョンを記録。サンプル問題3例を目視レビューしやすい形式で出す。
8. 必要な場合だけ既存UIへの接続まで進める。原則として**まず生成器＋ベンチマークが主成果**。徳川18枚／競走馬24枚の固定ステージや保存データを破壊しない。
